ShipCheck 공통 C# 검증 엔진 전환 계획
작성: 2026-10-29 / 개발 디렉터 리뷰
상태: 다음 작업 준비. 현재 R2-1~R2-5 수정과 검증을 먼저 완료한다.

1. 목적과 작업 경계
GUI가 PowerShell 검증 스크립트를 실행하는 구조를 C# 공통 엔진 호출로 전환한다.
GUI, CLI, SVN 커밋 훅이 동일한 정책, 결과, 오류 분류, 상태 식별과 테스트를 공유한다.
이번 준비 작업에서는 실행 코드와 현재 Claude Code의 수정 파일을 변경하지 않는다.
현재 수정 완료 보고와 검증 증거를 먼저 남긴 뒤 아래 순서로 전환한다.
현재 수정 결과는 아직 독립 재검증하지 않았으므로 통과 기준선으로 간주하지 않는다.

2. 현재 구조에서 확인한 근거
- Gui/ShipCheckMonitor/ShipCheckEngine.cs: powershell.exe 실행, 임시 결과 JSON 읽기.
- ShipCheck.ps1: 프로젝트/엔진 탐색, SVN 상태, 정책, 캐시, 빌드, 기록을 모두 소유.
- Gui/ShipCheckMonitor/Models.cs 및 Controls.cs: 오류 파싱/판정 일부가 스크립트와 중복.
- Tests/EngineHarness/EngineHarness.csproj: GUI 소스를 Compile Include로 직접 링크.
- ShipCommit.ps1 및 TortoiseSVN-PreCommit.cmd: 기존 검증 스크립트를 호출.
- 실행 파일은 ShipCheck.ps1을 찾지 못하면 시작할 수 없는 상태.

3. 목표 구조 (프로젝트 이름은 구현 시 기존 이름과 충돌 여부 확인)
ShipCheck.Core                  net8.0, UI/PowerShell 의존 없음
  요청/결과/오류 계약, 정책, 검증 순서, 상태 및 캐시 적합성 판정,
  변경 분류, 공통 빌드 진단 파서, 설정 우선순위, 화면 상태 판정에 필요한 순수 로직.
ShipCheck.Infrastructure        net8.0-windows
  SVN 호출/XML 파싱, 엔진 탐색, Build.bat 실행, 프로세스 트리 관리,
  Windows Job Object, 프로젝트 잠금, 파일 스냅샷, 설정/캐시/기록 저장.
ShipCheck.Cli                   net8.0-windows console
  query / validate / commit / hook 진입점, 인수 검증, 결과 JSON/콘솔 출력,
  종료 코드 매핑. 정책과 빌드 성공 판정은 Core에 위임.
기존 ShipCheckMonitor GUI
  Core 서비스 직접 호출. UI 이벤트/설정 편집/로그 표시/에디터 연결 담당.
  PowerShell 프로세스 및 결과 전달용 임시 JSON 파일을 사용하지 않는다.
Tests
  Core.Tests / Integration.Tests / Acceptance.Tests와 공유 fixture.
  테스트는 ProjectReference로 제품 어셈블리를 사용한다. 제품 소스 복제/링크 금지.

의존 방향: GUI와 CLI -> Core + Infrastructure; Infrastructure -> Core.
Core는 Process, WinForms, PowerShell, 전역 설정에 직접 접근하지 않는다.
필요한 외부 경계(프로세스, 저장소, 시간/잠금 등)에만 작은 인터페이스를 둔다.
불필요한 서비스 서버, 플러그인 프레임워크, 범용 계층은 추가하지 않는다.
Unreal Build.bat와 svn.exe는 외부 도구로 유지한다. 이들의 내부 기능은 재구현하지 않는다.
개발/배포용 .cmd가 남아도 무방하나 업무 정책이나 검증 판단은 넣지 않는다.

4. 공통 결과와 오류 처리 계약
- QueryAsync / ValidateAsync가 같은 명시적 요청/결과 타입을 사용한다.
- CancellationToken과 구조화된 진행 이벤트로 진행률/로그/취소를 전달한다.
- 결과에는 실행 ID, 프로젝트, 상태 식별자, 검증 범위, 단계별 종료 코드,
  진단 목록, 시작/종료 시간, 로그 위치, 캐시 재사용 여부, 정책상 허용 여부를 담는다.
- 빌드 실패, 설정 오류, SVN 상태 불명, 외부 실행 실패, 시간 초과,
  취소, 검증 중 변경, 저장 실패를 구분한다. 빈 목록/false로 오류를 숨기지 않는다.
- 진단에는 안정적인 코드, 단계, 사용자 설명, 원인/원본 stderr,
  가능한 파일/행 정보를 둔다. GUI와 CLI는 같은 진단을 표현만 달리한다.
- 실패 여부는 외부 도구 종료 코드를 우선한다. 로그 파서는 설명을 풍부하게 한다.
  파싱 가능한 오류 줄이 없더라도 nonzero exit를 성공으로 바꾸지 않는다.
- Pass/Cached/Skipped/Fail/Error/Canceled 및 기존 JSON 필드/종료 코드의 실제 의미를
  먼저 호환성 표로 고정한다. Skipped를 검증된 Pass로 표시하지 않는다.
- CLI의 기존 성공/차단/실행오류 0/1/2 계약을 확인하고 유지한다.
  취소/시간 초과/상태 불명/검증 중 변경은 커밋 허용 종료 코드로 매핑하지 않는다.
  우회 태그 등 기존 명시적 정책은 보존하되 사유와 사용 사실을 기록한다.
- 알 수 없는 예외는 실행 경계에서 오류 결과로 변환하고 원인을 로그에 보존한다.
  캐시 저장 실패와 검증 실패는 구분하되 저장 실패를 조용히 무시하지 않는다.

5. 정확성 불변 조건
- 상태 식별 계산은 UseCache와 독립적이다. 캐시를 꺼도 실패 표시/상태 비교는 동일하다.
- 프로젝트 탐색을 끝낸 뒤 명시적 ConfigPath > 프로젝트별 설정 > 공통 설정의
  우선순위를 적용한다. 기존 상대 경로 해석과 설정 저장 형식을 유지한다.
- SVN info로 실제 워킹 카피임을 확인한다. 상태 불명은 변경 없음이 아니다.
- XML 등의 구조화된 SVN 출력으로 경로/상태를 읽고 공백/한글 경로를 보존한다.
- 미등록 디렉터리 내부의 관련 소스, 삭제/교체, 혼합 리비전, 부분 커밋 범위를 반영한다.
- 잠금 획득 후 상태/검증 범위/누락 파일/캐시 적합성을 다시 평가한다.
- 빌드 전후 상태가 달라지거나 관측 중 오류가 나면 현재 상태의 통과를 저장하지 않는다.
  A -> B -> A 변경은 전후 해시만으로 발견할 수 없다는 한계를 별도로 검토한다.
  변경 감시를 쓰면 감시 누락/버퍼 초과도 무효 처리하고, 보장 범위를 문서화한다.
  안정된 입력 스냅샷 없는 검증을 원천적으로 완전한 보장이라고 표현하지 않는다.
- 캐시 키에는 정책, 엔진/타깃/인수, SVN 기준, 입력 내용과 검증 범위를 반영한다.
  인수 배열을 단순 공백 연결해 서로 다른 인수가 같은 키가 되지 않도록 한다.
- 캐시 스키마 버전을 두고 이전 형식은 보수적으로 무효화한다. 설정/이력은 보존한다.
- GUI와 CLI의 동시 실행은 같은 프로젝트 잠금 및 캐시 규약을 사용한다.
- 취소/시간 초과 시 손자 프로세스까지 종료하고 출력 배출, 잠금 해제, 임시 파일 정리를 보장한다.
- 외부 실행은 인수 경계를 보존한다. .bat 호출에 필요한 cmd 인용은 전용 경계에서 처리한다.
- 기록 쓰기는 원자적 교체/동시 쓰기 규칙을 공유한다. 손상된 캐시를 성공 근거로 삼지 않는다.

6. 단계별 전환 및 완료 증거
단계 0: 현재 5건 수정 종료
  Claude가 수정 파일, 실행 명령, 테스트 결과, 남은 제한을 보고한다.
  기존 22/21 테스트는 과거 결과일 뿐이다. 최신 수정본으로 다시 실행한 결과를 사용한다.
  R2-1~R2-5를 회귀 테스트에 포함하고 독립 재현으로 확인한다.
  현재는 Git 저장소가 아니므로 변경 전 기준선/복구 사본과 파일 해시를 별도 보존한다.
단계 1: 계약 및 테스트 기준선
  지원되는 명령/인수, JSON, 설정, 이력, 캐시, 훅 인수/종료 코드의 호환성 표 작성.
  공통 결과/진단 모델과 실패 상태 판정, 파서를 추출하고 독립 테스트 작성.
단계 2: Core/Infrastructure 및 CLI
  프로젝트 탐색 -> SVN -> 정책/스냅샷 -> 잠금/캐시 -> 빌드 -> 기록 순서로 이전.
  동일 fixture로 수정 완료된 기존 엔진과 새 엔진의 의미상 결과를 비교한다.
  시간/로그 경로 등 비결정적 필드를 제외하고 결과/허용 여부/진단/검증 범위를 비교한다.
  기존 구현의 알려진 결함은 동등성 기준으로 복제하지 않는다.
단계 3: GUI 직접 연결
  ShipCheckEngine의 PowerShell 래퍼를 Core 서비스 호출로 대체.
  설정 오류 시 설정 창 접근, 실패/취소/상태 불명 표시와 UI 응답성 검증.
  로그 파싱과 건강 상태 판정은 테스트 가능한 공통 로직을 사용.
단계 4: 훅 및 커밋 CLI 전환
  훅은 CLI로 연결하고 기존 TortoiseSVN PATH/DEPTH/MESSAGEFILE/CWD를 보존.
  검증 실패/취소/오류이면 svn commit을 호출하지 않는지 실제 실행 경계에서 검증.
  호환 스크립트가 필요하면 인수 전달만 남긴다. 이중 검증 엔진을 장기 유지하지 않는다.
단계 5: 배포/정리
  단일 솔루션의 dotnet test 진입점으로 자동 테스트를 실행하고 실패를 nonzero로 반환.
  새 엔진으로 전환한 뒤 구 PowerShell 업무 로직/임시 결과 전달 코드를 제거.
  깨끗한 배포 폴더에서 GUI와 CLI가 ShipCheck.ps1 없이 실행되는지 확인.
  배포 단위는 GUI/CLI와 필요한 DLL/설정 전체이며 단일 EXE라고 부풀리지 않는다.
  README, 빌드/배포 명령, 런타임 전제, 훅 설치와 이전/복구 절차를 갱신.

7. 테스트 구성과 필수 사례
Core 단위 테스트:
  설정 우선순위, 파일/모듈 분류, 정책, 검증 범위, 캐시 키/적합성,
  오류 파서, 상태 불명/취소/실패 구분, 캐시 비활성 상태의 실패 표시.
통합 테스트:
  임시 실제 SVN repo/wc + 제어 가능한 모의 빌드 프로세스.
  전용 C# 테스트 자식 프로세스로 대기/출력/실패/손자 실행을 재현한다.
  경쟁 조건은 신호/장벽으로 제어하고 임의 Sleep에 기대지 않는다.
  테스트 실행마다 별도 디렉터리와 제한 시간을 사용하고 실제 프로젝트를 건드리지 않는다.
인수 테스트:
  GUI 서비스 호출, CLI JSON/종료 코드, 훅과 commit 호출 여부를 동일 fixture로 비교.
  필요한 GUI 스모크 테스트는 별도로 명시하고 자동 테스트 통과와 구분한다.

필수 회귀 행렬:
  R2-1 빌드 중 변경 / 잠금 대기 중 변경 / 변경 후 원복.
  R2-2 미등록 폴더 내부 소스와 엄격 정책 / 이후 내부 파일 변경 캐시 무효화.
  R2-3 명시 프로젝트와 자동 탐색의 프로젝트별 설정 일치.
  R2-4 export 폴더 / SVN 누락 / stderr 오류를 변경 없음으로 표시하지 않음.
  R2-5 UseCache=false에서 실패 상태 유지.
  기존 정책 강화, 부분 검증 범위, 혼합 리비전, 헤더, 단독 컴파일, 우회 기록.
  동시 GUI/CLI 실행, 취소/시간 초과/자식 프로세스 종료, 비정상 종료 후 잠금 복구.
  공백/한글/따옴표 포함 경로 및 인수, 손상된 설정/캐시/이력, 쓰기 실패.
  실패한 검증에서 커밋 미실행, 구 훅 인수 호환, 배포 폴더 단독 스모크.

8. 최종 인수 조건
- GUI/CLI/훅이 같은 검증 엔진 및 오류 계약을 사용한다.
- 제품 런타임의 검증에 PowerShell 설치나 ShipCheck.ps1이 필요하지 않다.
- 테스트는 동일 제품 어셈블리를 참조하고 하나의 명령으로 결과를 집계한다.
- 기존 기능/설정/훅 동작 호환과 위 회귀 행렬의 증거를 제출한다.
- 개발자가 소스 트리를 갖고 있지 않아도 문서화된 배포 폴더로 실행 가능하다.
- 실제 Unreal 빌드의 성공/컴파일 실패/취소 확인은 별도 증거로 남긴다.
  환경이 없으면 자동 테스트 완료와 UE 실환경 미검증을 분리해서 보고한다.
- 단계별 수정 파일, 테스트 명령/결과, 호환성 차이, 남은 제한을 보고한다.
